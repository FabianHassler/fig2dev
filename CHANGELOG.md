# Changelog

## 0.9.4 — 2026-10-31

- PDF: centred and right-justified text in the standard 14 fonts (Times, Helvetica, Courier; the PDF names them and does not embed them) is placed with the Adobe Core 14 AFM advance widths, which is how the viewer draws them, instead of the widths of the installed or fallback font (`scene/afm.rs`). Left-justified text is unchanged.
- PDF pictures in PostScript and EPS output: axial and radial shadings (as the fill of a path, a shading pattern, or the `sh` operator) are written as PostScript Level 3 `shfill` vectors (the EPS says `%%LanguageLevel: 3`) instead of turning the whole page into one image. Transparency, function-based and mesh shadings, shadings used as strokes, and tiling patterns still make the page an image. PDF pictures encrypted with an empty user password (RC4, AES) are read, as hayro does; tests added.
- Hardening (B11), checked against fig2dev 3.2.9a built from source: `-L box` writes the whole-figure comments as `print_comments("% ", ...)` does (`%  text ` with the comment's bytes as read; was `% text`): 0 differences on the 2,554 sample figures (1,041 before). Pictures compressed as `.zip`, `.bz2`, `.bz` or `.xz` are read through `unzip -p`, `bunzip2 -c` and `unxz -c` as `open_stream` does (run directly, no shell; not on wasm). `-E ascii` (and `us-ascii`, `ANSI_X3.4-1968`, ...) converts strictly as iconv: text stops at the first byte beyond 0x7f with "Error converting string ...: Illegal byte sequence"; that message and the "Unable to convert" one show the text's bytes as they are (also non-UTF-8 bytes); a charset name with blanks is refused as iconv does. Left: netpbm's palette order for PPM, TIFF, XPM and GIF pictures (first use here), `-E utf-16` and the multibyte charsets' error positions.
- Fill patterns (41-62) in smoothed bitmaps (`-S 2`, `-S 4`): the pattern lines are drawn hard-edged at the bitmap's own resolution and enlarged, as ghostscript draws them (it ignores `GraphicsAlphaBits` inside a pattern cell), so inside a shape the pixels equal the unsmoothed bitmap's; only the shape's edge is smoothed. On a 22-pattern sheet against fig2dev (C, with gs) the share of pixels differing by more than a third of the range falls from 29.5% to 26.6% (`-S 2`) and from 26.1% to 25.2% (`-S 4`), unsmoothed 23.6%. New public field `RasterOptions::pattern_k` (1 for no supersampling).
- Bugs of fig2dev 3.2.9a no longer copied (the port follows what C means, not what it got wrong):
  - SVG: a line with arrows was clipped by the previous object's other arrowhead too (C keeps the arrowheads in function statics); each object now clips only its own.
  - LaTeX, epic, pict2e, PiCTeX, TikZ: a Symbol or ZapfDingbats character from a UTF-8 file is one `\charNNN` (`±` → `\char177`; C wrote one per UTF-8 byte, `\char194\char177`), as the SVG driver already did; a Latin-1 file whose text needs converting keeps its codes (C took it for UTF-8 and dropped them). Turning UTF-8 into Latin-1 drops only a character Latin-1 lacks, not the characters after it.
  - MetaPost: the forward arrowhead of an approximated spline sits on the last point (C put it on the last point but one).
  - Gerber: `%SF…*%` and circular apertures `%ADD…C,…*%` end in `*%` (C wrote `%` and `%*`); the `D02` that ends a filled polygon or an arc ends its block (C left it on the next block's line), and no empty block is written before a flash.
  - `-h -L mf`: `-Y ymax` (C's help says `-Y xmax`).
  - SVG: shades and tints of a colour with red in it (fill 1-19, 21-39) had a wrong colour (C's blue mask let the red byte in: a half shade of red was `#7f807f`, now `#7f0000`).
  - Tk: `-g` puts `-bg` inside `[canvas …]` (C wrote it after the `]`, a Tcl error) with 8-bit channels (C divided the 16-bit ones by 255: white was `#101101101`).
  - PSTricks: user colours are divided by 255 (C: 256, so 255 never reached 1).
  - DXF: rounded boxes span their corners (C compared the flipped y with the raw y); ellipses take the longer radius as the major axis (ratio at most 1, as DXF requires) and are turned by their angle (C ignored it); the picture warning says DXF (C: "IBMGL").
  - LaTeX: dark brown is `.5,.19,0` (128, 48, 0; C: `.17`).
  - PiCTeX, TextYL, epic (short arcs): arc arrowheads point along the arc as in the SVG driver (C turned them over by mixing y-up and y-down conventions); epic rounds both coordinates of the arrowhead's base.
  - TikZ: open arcs keep their cap style (C tested the arc type the wrong way round, so wedges got it instead); turned ellipses keep a tenth of a degree (C rounded to whole degrees).
  - epic, PiCTeX: turned ellipses are turned (a quarter turn swaps the radii, other angles draw a 72-point polygon; C drew every ellipse unturned).
  - EMF: a turned text's bounds are its four corners (C took the end's y with the wrong sign); arc direction and the arrowhead test are computed in 64 bits (C's int overflowed beyond about 38 inches and turned arcs round).
  - CGM: the standard colours are xfig's 8-bit values (C truncated its float table: 175 for 176, 214 for 215).

## 0.9.3 — 2026-10-28

- On crates.io as `figbase`, `fig2dev-rs-lib` (the library, still `fig2dev::…` in code) and `fig2dev-rs` (`cargo install fig2dev-rs` installs the `fig2dev` program); the name `fig2dev` stays the C program's. Packages renamed: `fig2dev` → `fig2dev-rs-lib`, `fig2dev-cli` → `fig2dev-rs`. The packages carry the licence texts (MIT, Apache-2.0 and xfig's notice, SPDX `(MIT OR Apache-2.0) AND Xfig`), keywords and the README.
- Drawing order: objects that share a depth are drawn in xfig's order (arcs, compounds, ellipses, lines, splines, texts, each in file order), in every output language, so the output looks like xfig's screen. fig2dev 3.2.9a sorts them with the C library's `qsort`, whose order of equal depths depends on the C library (this port followed macOS's until now).

- `-h` lists only the general options and the languages; `-h -L <lang>` (or `-L <lang> -h`, as in C) adds that language's options. The C program's `-h` lists every language's options.

## 0.9.0 — 2026-10-26

- Hardening (RustFig B11), checked against fig2dev 3.2.9a: fig2dev's own test suite passes 88 of 88 (was 82, 6 failing).
- SVG is now written by `drivers/svg.rs`, a port of `gensvg.c` object by object: byte-identical with C on 284 of 299 sample figures (the rest: Latin-1 text C writes as invalid UTF-8, written as valid UTF-8 here). Texts with a `# rustfig-font:` comment keep the installed family first. Symbol and ZapfDingbats texts read from UTF-8 take one code per character (Latin-1 files go byte by byte, as in C).
- Bitmaps: without smoothing, shapes grow by ghostscript's `fill_adjust` and embedded EPS pictures are hard-edged, as gs draws them (`RasterOptions::adjust_px`, new public field); with `-S 2`/`-S 4` strokes widen as gs's alpha bits make them. `-N` greys embedded EPS pictures.
- EPS/PDF: a dash style value of 0 draws solid (as `genps`); the PDF MediaBox is the integer bounding box (as ps2pdf), and PDF files carry an XMP metadata packet.
- Options and messages as `fig2dev.c`: `-f` with an unknown font warns and goes on, `-b` may be negative, `-V` and `-h` (also `-L <lang> -h`) print C's text; no stale "planned" labels (only `-j` stays unported).
- Test harness: koi8-r iconv names, `AS_ECHO` expanded, `test2` (MediaBox probe) ported to Rust.

## 0.8.0 — 2026-10-23

- Installed fonts per text (RustFig F7): a text whose comment is `# rustfig-font: <Family Style>` is set in that installed font (found through figbase's `fontdb`; new `figbase::text::{find_local_font, LocalFont, parse_local_font_comment}`, `TextPrim::local_font`), with the Fig font number as the fallback. PDF embeds a subset (CID font, Identity-H, TrueType `FontFile2` or OpenType-CFF `FontFile3`, widths and ToUnicode from the font); PostScript and EPS embed TrueType subsets as Type 42 fonts and draw CFF fonts as outlines; SVG writes `font-family=\"'Family', <the Fig font's families>\"` (no font data embedded); bitmaps use the font's outlines. A font whose `fsType` forbids embedding (restricted licence, no subsetting, bitmaps only) is drawn as outlines in PDF and PostScript, with a message. A family that is not installed falls back to the Fig font with a message (stderr); the LaTeX-family drivers ignore the comment and keep the Fig number. Output for figures without the comment is unchanged. New dependency: `subsetter` 0.2 (typst's font subsetter, default features off, so no `skrifa`), and `fontdb` as a dev-dependency of `fig2dev`. Tests: `tests/local_fonts.rs` (use a font found at test time, skip without one).

- Hardening pass (B11): `\ooo` text escapes pinned against fig2dev 3.2.9a's `read_textobject` (short escapes, `\000`, values above `\377` wrap, `\12x` consumes three characters, `\8` is a read error), byte-identical output for latex and pstricks; hostile figures (coordinates at the i32 limits, huge fonts, degenerate splines) checked in 20 languages without panics. `-L sld` has no C driver of its own: fig2dev pipes the ppm through `ppmtoacad`, which the port reproduces.

## 0.6.0 — 2026-10-21

- PDF and EPS picture objects as vectors (RustFig B15; MSRV is now Rust 1.92, `pdf-writer` 0.15, new dependencies `hayro` and `hayro-write`). `util::pdfpic::PdfPicture` reads the first page of a PDF file (the `hayro` crates; every call guarded against panics); `LoadedPicture::Pdf` is now `Pdf(Option<PdfPicture>)`. PDF output embeds the page as a Form XObject (new `Prim::PdfPicture`; `to_pdf_pages` takes the embedded pictures, which also lets JPEG pictures keep their data, `/DCTDecode`, where they were decoded pixels). PostScript and EPS output (new `TextOptions::ps_pictures`) embed the page as EPS made by `util::pdfps` (a PostScript device on `hayro-interpret`, the `pdftops` step of C); a page with opacity, soft masks, blend modes, shadings or tiling patterns is written as one image, with a message. Bitmaps and the canvas render the page (`raster::rasterize`). EPS pictures in PDF and bitmap output (new `TextOptions::eps_via_gs`) go through ghostscript when installed (`util::gs`: `gs` found on `PATH` at run time, no shell, `-dSAFER -dEPSCrop -sDEVICE=pdfwrite`, 60 s and 256 MB limits, results cached; not on wasm); without it nothing changes (preview image in bitmaps; left out in PDF, with a message about ghostscript). `EmbeddedEps` and the writers' other signatures are otherwise unchanged; output for figures without PDF or EPS pictures is unchanged. Tests: `tests/pdf_pictures.rs`, `tests/pdf_gs_missing.rs`, `tests/pdf_pictures_reference.rs` (against the C program).

## 0.5.0 — 2026-10-21

- The reader's repairs and checks as functions (RustFig D7: export from objects without Fig text): `read::repair_line` (`sanitize_lineobject`: close, convert and unfill boxes, polygons and polylines; returns what the reader says as `LineNote`s, or a `LineFault`), `read::repair_arc` (`sanitize_arc`), `read::{arc_invalid, line_invalid, spline_invalid, ellipse_invalid, text_invalid, common_invalid}` (the field checks), `read::arrow_fault` (`make_arrow`'s refusals), `read::apply_font_size` (`-s` on a text) and `read::trim_text_start` (the blanks `sscanf` drops before a text). The reader calls them, so a figure built in memory gets exactly what a file gets; no change to the reader's or the drivers' output or messages.

## 0.4.0 — 2026-10-20

- Reading for an editor (RustFig D3): `Ctx::editing` (default `false`, which leaves the reader and every driver exactly as fig2dev's) makes `read::readfp_fig` read as xfig's `f_read.c` does, not as fig2dev's `read.c`. Kept as written, where fig2dev repairs or refuses: arcs off their circle (no `sanitize_arc`), open polygons, distorted boxes, boxes and polygons with few points (xfig deletes a box, arc-box or picture with fewer than 5 points and a polygon with fewer than 3, with a message, instead of converting them), the fill of 2-point polylines, ellipses of radius 0, NUL bytes (a line ends there, as `fgets` and C strings do). Done as xfig does: depth clamped to 0..999 and fill style fixed (`fix_depth`, `fix_fillstyle`), ellipse and text angles turned into 0 to 2 pi (`fix_angle`), an unknown text font or justification set to the default with a message, a text keeps its leading blanks beyond the one that separates it from the fields (fig2dev's `sscanf` drops them all), a file of ASCII only is ISO-8859-1 (fig2dev: UTF-8), Fig 3.2 X-splines stay splines with their shape factors (fig2dev converts them to lines; `splines_to_lines` still does for the drivers), the fill colour of an unfilled object is renumbered like the other colours. The Fig 1.3 reader (`read1_3`) is unchanged. Not in fig2dev.
- `Ctx::header_transparent`: the transparent colour's number as the header gives it (`-2` none, `-1` background), which `gif_transparent` (a colour) cannot tell. Set by the reader in every mode; the default is `-2`. Not in fig2dev.

## 0.2.0 — 2026-10-20

- Hardening leftovers (2026-10-19): a picture that can't be read draws nothing in eps/ps/pdf and the bitmaps (as genps), and svg links every picture as gensvg does (`<image xlink:href="file:NAME">` with its rotate/flip transform, no read, no message); an indexed picture with one transparent colour (grey PNG with `tRNS` or alpha) is written opaque as genps's `indexed_image` does; `-L emf` to a pipe or terminal keeps the first header, prints genemf's fseek message and exits 255, to a file or `/dev/null` unchanged. API: `TextOptions.genps` now also drops unreadable pictures, new `TextOptions.link_pictures`, `Prim::LinkedImage`, `Ctx.output_unseekable`, `readpics::{load_picture_genps, pic_to_raster_as}`; `TextOptions::default()` (the canvas) keeps the crossed-box placeholder.
- `-L sld` (AutoCAD slide): the rasteriser's pixels encoded as `ppmtoacad -quiet` writes a slide (17-byte header with the NUL, size, aspect, each colour mapped to the nearest of AutoCAD's 256 colours, one vector per run, colour 0 skipped; netpbm's colour-depth halving above 32,767 colours). Byte-identical to the reference `ppmtoacad` run on our own `-L ppm` output, and equal in header and size to the reference's sld on all 311 fixture and sample figures; pixels differ from ghostscript's as for every bitmap language. Messages as the other bitmaps (`-q`, `-t`).

- FMA audit of the remaining drivers (audit pass 25b): every `gen*.c` compiled with `-ffp-contract=on` and `off` (arm64 clang -O2), the fused multiply-adds mapped to source and compared with the Rust ports. Already fused and confirmed: emf (57 sites), ibmgl (59, shared with dxf's splines, 12), map (11), pict2e (99), pstricks (47), tk/ptk (20 each), tikz (9). Added: latex (11 source lines: `round4`, slope/length, dash `round`, arc radius and tolerance, `\unitlength`), pictex (22 asm sites: `rtop`, arrow head, splines, arc angle), epic (34: arc points, `arc_arrow`, arrow head and its `x2 - P*0.7`, dash `round`, splines), textyl (21), pic and tpic (13 and 14: splines, `HT_OFFSET` baseline, tpic's `TEXFONTMAG` round), cgm (`len -= ARROW_EXTRA_LEN`, `round(1200*cos)`), and the shared `TEXFONTMAG`/`select_font` `round(size*mag)` (mp, pstricks, latex family). No fused sites in box, ge, mf. `round(a*b)` is now `fig2dev::round_mul`. 3,000 random figures x 22 languages x several `-m`: epic's arc differed (`-0.000` vs `0.000`, test `arc_points_are_fused_like_the_reference`), nothing else. Left: genps/gensvg's 13 and 6 fused sites belong to the scene code (not audited here).

- Plotter-driver details (audit pass 25): a driver's `exit(1)` keeps the output written so far, as C's stdio flush does (new `fig2dev::convert_partial` returns the bytes with the error; `convert` is unchanged; the standalone fig2dev writes them before the message; gbx running out of apertures leaves 84 KB on the reference and here); gbx `length()` and shape's arc, ellipse and arc-box vertices use fused multiply-adds as clang compiles gengbx.c/genshape.c (found by diffing `-ffp-contract=on/off` assembly; no difference on 1,700 random shapes or the 300-figure sample, the same either way); `%g`/`%f` of NaN print `nan` without a sign as macOS does (shape, epic, reader). Left: gbx's creation date is UTC without `SOURCE_DATE_EPOCH` (C: local time).

- Small helpers as C has them (audit pass 26): `SOURCE_DATE_EPOCH` accepts negative values (as `strtoull`) and years up to 2147485547, no-digit values give macOS's "strtoull: Invalid argument", and the time and a bad-value message come once per run (C's static `struct tm`); latex/pictex `set_color` looks user colours up by definition order (32 + index) instead of the file's colour number; `read_pdf` scans lines as readeps.c's `scan_mediabox` does (511-byte `fgets` pieces, the `[` anywhere after the key on its line; a box on a later line is still read, as ghostscript would find it); latex `-a`'s message has no newline, so the next one continues its line; `figbase`'s `x_color` no longer trims blanks (`lookup_X_color` doesn't); help text: `-Y xmax` (sic) for mf, the pstricks `-R` continuation indent, the `PSTricks` title, "inferrred" and the trailing blank of `-Z` as in `help_msg`. Already right and now tested: the colour table (658 entries, identical), `round()`.
- Map and png bounds (audit pass 23): the image map's whole-figure area and the png's size agree as in the reference for `-m`, `-b`, `-b` with `-m` (the map adds the border unscaled, the png scales it, in C too), metric, on all 311 fixture and sample figures (before and after: identical to fig2dev); bitmaps accept a negative `-b` (`n = (int)(b * 15 + 0.9)`, truncating) and cut the figure, as genbitmaps.c does (test `map_and_png_bounds_agree`).
- JPEG DCT passthrough (audit pass 19): eps/ps/pstex embed a JFIF or Exif JPEG as genps does, without decoding it: `AnalyzeJPEG` reads size, components and the Adobe marker, and `JPEGtoPS`'s EPS wrapper (`/DCTDecode`, `/Decode`, the CMYK Adobe inversion, `%%Creator: jpeg2ps by Thomas Merz in fig2dev 3.2.9a`) carries the file's bytes ASCII85-encoded as encode.c writes them; readjpg.c's messages ("unexpected end of JPEG file!", "DNL marker not supported...", "unknown color space") precede "NAME: Bad JPEG format". The block equals the reference's on all 15 test JPEGs with a data block (before: 0, the pixels were written as hex), the messages on the 8 error cases. C loops forever on a file without a further marker; here it is an "unexpected end" error. PDF and the bitmap languages still draw decoded pixels.
- Picture reading as the C readers do (audit pass 18): PNG always through the `read_png` port (file palette order, libpng's gamma/composition arithmetic with `gAMA`, `bKGD` and `-g`, `tRNS` as `num_transp`/`transp_cols`, libpng's warning and error lines, interlace warning), GIF through the `gif` crate with the transparent colour found again in the colour map (`Pic.transp_cols`), PCX/XBM/PPM as literal ports of readpcx.c/readxbm.c/readppm.c (C's scanline, padding and end-of-data quirks), XPM `None` black and no transparency, GIF/PPM/TIFF/XPM as PCX pictures, `pic_type` as genps's table (no P1-P5, no JPEG without JFIF/Exif), failures as "NAME: Bad TYPE format". Image data, palette and stderr equal the reference on 109 of 128 test pictures (before: 46 of the first 110); the rest are the reference's crashes and external-tool noise, 16-bit gamma rounding and palette TIFFs. EPS: a colour-keyed picture writes the key for its transparent pixels (a non-white key never masked).
- Header metadata (audit pass 16): eps/ps write `%%Title` (`-n`, else the input name, else stdin), `%%Creator: fig2dev Version 3.2.9a`, `%%CreationDate` (`SOURCE_DATE_EPOCH`, else UTC now), `%%Magnification`, the `%%DocumentNeededResources` CMap lines for non-ASCII text and the whole-figure comments before the prolog, in genps's order (no `%%HiResBoundingBox`/`%%LanguageLevel`); svg writes gensvg's preamble, Creator/CreationDate/Magnification comments, `<svg>` with `width`/`height` in points, `<desc>` comments and the `<g fill="none">` wrapper; pdf has an Info dictionary (Title, Creator, Producer, CreationDate, ModDate). Header blocks equal fig2dev's on 311/311 fixtures and sample figures (tests/header_meta.rs).
- Split out of the RustFig repository with its history: crates `figbase` and `fig2dev` (library) and the `fig2dev` program (package `fig2dev-cli`).
- FMA parity with the reference binary (audit pass 12): `ellipse_bound` (2 fused ops), `arc_bound` radius and trans_spline (blend functions, point weights, float step angle) fuse `a*b+c` as clang does; exact against oracle programs on 412,800 ellipses and 20,000 splines (tests/fma_oracle.rs). The "closed spline with less than three points" message has no newline, as in C.
