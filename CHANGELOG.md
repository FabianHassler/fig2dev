# Changelog

## 0.5.0 — 2026-10-21

- The reader's repairs and checks as functions (RustFig D7: export from objects without Fig text): `read::repair_line` (`sanitize_lineobject`: close, convert and unfill boxes, polygons and polylines; returns what the reader says as `LineNote`s, or a `LineFault`), `read::repair_arc` (`sanitize_arc`), `read::{arc_invalid, line_invalid, spline_invalid, ellipse_invalid, text_invalid, common_invalid}` (the field checks), `read::arrow_fault` (`make_arrow`'s refusals), `read::apply_font_size` (`-s` on a text) and `read::trim_text_start` (the blanks `sscanf` drops before a text). The reader calls them, so a figure built in memory gets exactly what a file gets; no change to the reader's or the drivers' output or messages.

## 0.4.0 — 2026-10-20

- Reading for an editor (RustFig D3): `Ctx::editing` (default `false`, which leaves the reader and every driver exactly as fig2dev's) makes `read::readfp_fig` read as xfig's `f_read.c` does, not as fig2dev's `read.c`. Kept as written, where fig2dev repairs or refuses: arcs off their circle (no `sanitize_arc`), open polygons, distorted boxes, boxes and polygons with few points (xfig deletes a box, arc-box or picture with fewer than 5 points and a polygon with fewer than 3, with a message, instead of converting them), the fill of 2-point polylines, ellipses of radius 0, NUL bytes (a line ends there, as `fgets` and C strings do). Done as xfig does: depth clamped to 0..999 and fill style fixed (`fix_depth`, `fix_fillstyle`), ellipse and text angles turned into 0 to 2 pi (`fix_angle`), an unknown text font or justification set to the default with a message, a text keeps its leading blanks beyond the one that separates it from the fields (fig2dev's `sscanf` drops them all), a file of ASCII only is ISO-8859-1 (fig2dev: UTF-8), Fig 3.2 X-splines stay splines with their shape factors (fig2dev converts them to lines; `splines_to_lines` still does for the drivers), the fill colour of an unfilled object is renumbered like the other colours. The Fig 1.3 reader (`read1_3`) is unchanged. Not in fig2dev.
- `Ctx::header_transparent`: the transparent colour's number as the header gives it (`-2` none, `-1` background), which `gif_transparent` (a colour) cannot tell. Set by the reader in every mode; the default is `-2`. Not in fig2dev.

## 0.3.0 — 2026-10-20

- Building figures in memory (RustFig D8): `Ctx::for_figure(ppi, metric, colors)`, `Figure { ctx, objects }` (with `convert`), `trans_spline::splines_to_lines` (X-splines to lines as the reader does). No change to the program or its output.
- The command line is in the library (D10): `fig2dev::cli::run(args, stdin, stdout, stderr) -> exit code` (not on wasm); the `fig2dev` binary is a thin `main` around it, output and exit status unchanged.

## 0.2.0 — 2026-10-20

- Hardening leftovers (2026-10-19): a picture that can't be read draws nothing in eps/ps/pdf and the bitmaps (as genps), and svg links every picture as gensvg does (`<image xlink:href="file:NAME">` with its rotate/flip transform, no read, no message); an indexed picture with one transparent colour (grey PNG with `tRNS` or alpha) is written opaque as genps's `indexed_image` does; `-L emf` to a pipe or terminal keeps the first header, prints genemf's fseek message and exits 255, to a file or `/dev/null` unchanged. API: `TextOptions.genps` now also drops unreadable pictures, new `TextOptions.link_pictures`, `Prim::LinkedImage`, `Ctx.output_unseekable`, `readpics::{load_picture_genps, pic_to_raster_as}`; `TextOptions::default()` (the canvas) keeps the crossed-box placeholder.
- `-L sld` (AutoCAD slide): the rasteriser's pixels encoded as `ppmtoacad -quiet` writes a slide (17-byte header with the NUL, size, aspect, each colour mapped to the nearest of AutoCAD's 256 colours, one vector per run, colour 0 skipped; netpbm's colour-depth halving above 32,767 colours). Byte-identical to the reference `ppmtoacad` run on our own `-L ppm` output, and equal in header and size to the reference's sld on all 311 fixture and sample figures; pixels differ from ghostscript's as for every bitmap language. Messages as the other bitmaps (`-q`, `-t`).

- FMA audit of the remaining drivers (audit pass 25b): every `gen*.c` compiled with `-ffp-contract=on` and `off` (arm64 clang -O2), the fused multiply-adds mapped to source and compared with the Rust ports. Already fused and confirmed: emf (57 sites), ibmgl (59, shared with dxf's splines, 12), map (11), pict2e (99), pstricks (47), tk/ptk (20 each), tikz (9). Added: latex (11 source lines: `round4`, slope/length, dash `round`, arc radius and tolerance, `\unitlength`), pictex (22 asm sites: `rtop`, arrow head, splines, arc angle), epic (34: arc points, `arc_arrow`, arrow head and its `x2 - P*0.7`, dash `round`, splines), textyl (21), pic and tpic (13 and 14: splines, `HT_OFFSET` baseline, tpic's `TEXFONTMAG` round), cgm (`len -= ARROW_EXTRA_LEN`, `round(1200*cos)`), and the shared `TEXFONTMAG`/`select_font` `round(size*mag)` (mp, pstricks, latex family). No fused sites in box, ge, mf. `round(a*b)` is now `fig2dev::round_mul`. 3,000 random figures x 22 languages x several `-m`: epic's arc differed (`-0.000` vs `0.000`, test `arc_points_are_fused_like_the_reference`), nothing else. Left: genps/gensvg's 13 and 6 fused sites belong to the scene code (not audited here).

- Plotter-driver details (audit pass 25): a driver's `exit(1)` keeps the output written so far, as C's stdio flush does (new `fig2dev::convert_partial` returns the bytes with the error; `convert` is unchanged; the standalone fig2dev writes them before the message; gbx running out of apertures leaves 84 KB on the reference and here); gbx `length()` and shape's arc, ellipse and arc-box vertices use fused multiply-adds as clang compiles gengbx.c/genshape.c (found by diffing `-ffp-contract=on/off` assembly; no difference on 1,700 random shapes or the 300-figure sample, the same either way); `%g`/`%f` of NaN print `nan` without a sign as macOS does (shape, epic, reader). Left: gbx's creation date is UTC without `SOURCE_DATE_EPOCH` (C: local time).

- Small helpers as C has them (audit pass 26): `SOURCE_DATE_EPOCH` accepts negative values (as `strtoull`) and years up to 2147485547, no-digit values give macOS's "strtoull: Invalid argument", and the time and a bad-value message come once per run (C's static `struct tm`); latex/pictex `set_color` looks user colours up by definition order (32 + index) instead of the file's colour number; `read_pdf` scans lines as readeps.c's `scan_mediabox` does (511-byte `fgets` pieces, the `[` anywhere after the key on its line; a box on a later line is still read, as ghostscript would find it); latex `-a`'s message has no newline, so the next one continues its line; `figbase`'s `x_color` no longer trims blanks (`lookup_X_color` doesn't); help text: `-Y xmax` (sic) for mf, the pstricks `-R` continuation indent, the `PSTricks` title, "inferrred" and the trailing blank of `-Z` as in `help_msg`. Already right and now tested: the colour table (658 entries, identical), `round()`.
- Map and png bounds (audit pass 23): the image map's whole-figure area and the png's size agree as in the reference for `-m`, `-b`, `-b` with `-m` (the map adds the border unscaled, the png scales it, in C too), metric, on all 311 fixture and sample figures (before and after: identical to fig2dev); bitmaps accept a negative `-b` (`n = (int)(b * 15 + 0.9)`, truncating) and cut the figure, as genbitmaps.c does (test `map_and_png_bounds_agree`).
- JPEG DCT passthrough (audit pass 19): eps/ps/pstex embed a JFIF or Exif JPEG as genps does, without decoding it: `AnalyzeJPEG` reads size, components and the Adobe marker, and `JPEGtoPS`'s EPS wrapper (`/DCTDecode`, `/Decode`, the CMYK Adobe inversion, `%%Creator: jpeg2ps by Thomas Merz in fig2dev 3.2.9a`) carries the file's bytes ASCII85-encoded as encode.c writes them; readjpg.c's messages ("unexpected end of JPEG file!", "DNL marker not supported...", "unknown color space") precede "NAME: Bad JPEG format". The block equals the reference's on all 15 test JPEGs with a data block (before: 0, the pixels were written as hex), the messages on the 8 error cases. C loops forever on a file without a further marker; here it is an "unexpected end" error. PDF and the bitmap languages still draw decoded pixels.
- Picture reading as the C readers do (audit pass 18): PNG always through the `read_png` port (file palette order, libpng's gamma/composition arithmetic with `gAMA`, `bKGD` and `-g`, `tRNS` as `num_transp`/`transp_cols`, libpng's warning and error lines, interlace warning), GIF through the `gif` crate with the transparent colour found again in the colour map (`Pic.transp_cols`), PCX/XBM/PPM as literal ports of readpcx.c/readxbm.c/readppm.c (C's scanline, padding and end-of-data quirks), XPM `None` black and no transparency, GIF/PPM/TIFF/XPM as PCX pictures, `pic_type` as genps's table (no P1-P5, no JPEG without JFIF/Exif), failures as "NAME: Bad TYPE format". Image data, palette and stderr equal the reference on 109 of 128 test pictures (before: 46 of the first 110); the rest are the reference's crashes and external-tool noise, 16-bit gamma rounding and palette TIFFs. EPS: a colour-keyed picture writes the key for its transparent pixels (a non-white key never masked).
- Header metadata (audit pass 16): eps/ps write `%%Title` (`-n`, else the input name, else stdin), `%%Creator: fig2dev Version 3.2.9a`, `%%CreationDate` (`SOURCE_DATE_EPOCH`, else UTC now), `%%Magnification`, the `%%DocumentNeededResources` CMap lines for non-ASCII text and the whole-figure comments before the prolog, in genps's order (no `%%HiResBoundingBox`/`%%LanguageLevel`); svg writes gensvg's preamble, Creator/CreationDate/Magnification comments, `<svg>` with `width`/`height` in points, `<desc>` comments and the `<g fill="none">` wrapper; pdf has an Info dictionary (Title, Creator, Producer, CreationDate, ModDate). Header blocks equal fig2dev's on 311/311 fixtures and sample figures (tests/header_meta.rs).
- Split out of the RustFig repository with its history: crates `figbase` and `fig2dev` (library) and the `fig2dev` program (package `fig2dev-cli`).
- FMA parity with the reference binary (audit pass 12): `ellipse_bound` (2 fused ops), `arc_bound` radius and trans_spline (blend functions, point weights, float step angle) fuse `a*b+c` as clang does; exact against oracle programs on 412,800 ellipses and 20,000 splines (tests/fma_oracle.rs). The "closed spline with less than three points" message has no newline, as in C.
